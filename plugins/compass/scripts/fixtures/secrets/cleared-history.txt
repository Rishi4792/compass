# HISTORICAL FINDINGS CLEARED BY NAME — for `secret-scan --commits` ONLY.
#
# WHY THIS FILE HAS TO EXIST. `--commits` judges committed PATCHES, not the working tree, and that
# is deliberate: a real secret committed once is compromised even if the next commit deletes it, so
# a finding in history cannot be cleared by editing a file. That rule is right for secrets and it is
# therefore also permanent for FALSE alarms. Without a way to name one, a project's own release step
# fails for ever on a line that was never a secret, and the only routes left are rewriting published
# history or switching the check off. Both are worse than naming the line.
#
# THE LINE IS NAMED BY ITS HASH, NEVER BY ITS TEXT. The first version of this file recorded the
# offending line verbatim, and the tree scan failed on this file immediately — because a list of
# secrets contains secrets. That is the same mistake this release made six separate times: quoting
# the thing being removed re-creates it. A list of cleared findings is the last place that should
# hold the text of one. The hash is of the line with its outer whitespace trimmed.
#
# WHAT AN ENTRY DOES. It clears ONE finding: one path, and one exact line. Not a file, not a
# pattern, not a commit, not a prefix. One character different gives a different hash and the
# finding stands. Nothing here can clear a line nobody has in front of them, which is the property
# that makes this safe to have at all.
#
# WHAT AN ENTRY IS NOT. It is not a judgement that the line is harmless. It is a record that a named
# person looked at it and decided. If you are clearing something because it is inconvenient rather
# than because it is not a secret, the reason line will say so to the next reader — and it will
# clear a real key just as readily, which is exactly why the signer is required.
#
# Every use is COUNTED AND PRINTED in the summary, so these cannot quietly accumulate, and a
# clearance that matches nothing is reported too: one nobody re-checked is worth deleting.
#
# TO ADD ONE, take the hash from the SCANNER'S OWN OUTPUT, never from a line you reconstruct by
# hand. The first attempt at this entry rebuilt the line with `git show | grep` and produced a hash
# that matched nothing, because the grep selected a neighbouring line. The scanner already prints
# the exact text it objected to, so use that and nothing else:
#
#   compass.sh secret-scan --commits <range> 2>&1 | grep -E '^<path>:[0-9]+:' \
#     | head -1 | sed 's/^[^:]*:[0-9]*://' \
#     | sed 's/^[[:space:]]*//; s/[[:space:]]*$//' | shasum -a 256
#
# Then confirm which commit it came from before you sign anything, so the reason names a real one:
#
#   git rev-list <range> | while read c; do git show "$c" -- <path> | grep -q '^+.*<a fragment>' \
#     && git log -1 --oneline "$c"; done
#
# Format, one per line:   <path> :: sha256:<hex> :: <reason> :: <who, when>
